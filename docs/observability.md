# SYCO23 SETCRAWLER observability and release operations

This runbook defines the code-owned observability gate for issue #6. It covers
the API, metadata provider workers, process worker, and the single beat
scheduler. It does not enable audio or media acquisition.

## Log contract and correlation

Production application processes write one JSON object per line to standard
output. Docker Compose provides one host-level view across services and retains
at most five 10 MB files per container with the `local` driver. This bounds
local disk usage; operators may forward the Docker stream to a longer-lived
central sink without changing the application format.

Every record includes `timestamp`, `level`, `service`, `environment`, `logger`,
`event`, and `message`. Relevant records also include:

- `request_id`, accepted from a safe `X-Request-ID` or generated by the API;
- `job_id`, copied from the durable import job into API dispatch and Celery task
  records;
- `task_id` and `task_name` for worker and beat activity;
- `provider`, sourced from the provider descriptor dispatch header.

Search for one import across the stack with its sanitized UUID:

```bash
docker compose --env-file .env.production -f docker-compose.production.yml \
  logs --no-color api worker-provider-api worker-provider-scrape worker-process worker-beat \
  | grep '"job_id":"<sanitized-job-uuid>"'
```

Never log request or response bodies, authorization headers, cookies, complete
database/Redis URLs, Supabase keys, or provider credentials. The formatter
redacts secret-named fields, bearer values, credentials embedded in URLs, and
configured backend secret values before serialization. Evidence must still be
reviewed before it is attached to GitHub.

## Health and readiness

`GET /health` preserves the public `status`, `service`, `ready`, and `providers`
fields and adds aggregate `dependencies` and `alerts` fields. It never returns
connection strings, worker hostnames, exception messages, job IDs, or provider
credentials.

Production readiness checks:

- `postgres`: runs the aggregate import-job metrics query;
- `redis`: performs a bounded ping;
- `worker_queues`: compares active Celery queues with workloads derived from
  enabled provider descriptors plus the core `process` queue;
- `beat`: verifies a recent successful periodic-task heartbeat. The heartbeat
  proves the beat-to-queue-to-worker path executed, rather than only checking
  that a beat process exists.

The public endpoint caches the bounded dependency work for
`HEALTH_PROBE_CACHE_SECONDS` (10 seconds by default), preventing public polling
from turning the PostgreSQL aggregate or Celery inspection into an unbounded
per-request workload.

The API remains a liveness endpoint with HTTP 200, while `ready=false` marks a
dependency or required queue as unavailable. In fixture/local environments,
external dependency probes are reported as `not_checked` and do not make local
development depend on production services.

## Alert conditions

The health snapshot emits only aggregate values and configurable thresholds:

| Code | Default threshold | Response |
|---|---:|---|
| `dead_letter_growth` | 1 | Inspect the terminal error code, preserve the durable row, and retry only after the cause is corrected. Track increases between health snapshots. |
| `redrive_publish_failures` | 1 | Check Redis and queue routing; do not reset PostgreSQL job history or retry budgets. |
| `stuck_processing_jobs` | 1 | Confirm the claim is older than `JOB_CLAIM_TTL_SECONDS`, then verify the redriver republishes it once. |
| `provider_quota_failures` | 1 | Pause the affected provider workload or wait for quota recovery; never rotate a key into logs or evidence. |
| `provider_robots_failures` | 1 | Keep the provider blocked and re-check written permission and robots policy. Never fail open. |

An external HTTPS monitor should sample `/health` once per minute and alert
when `ready` is false, an alert changes from inactive to active, or a counter
increases. Route critical alerts to the operations on-call and warnings to the
provider-operations queue. Provider warnings do not by themselves make the API
unready; missing dependencies and required queues do.

## Service level objectives

### Import latency SLO

At least 95% of accepted metadata-only URL imports should reach a terminal
state (`completed`, `failed`, `blocked`, or `dead_letter`) within five minutes,
measured over a rolling 30-day window from `created_at` to `finished_at`.
Provider-policy blocks count as terminalized work; operator-created future
retries are excluded until `next_retry_at`.

### Job terminalization SLO

At least 99% of jobs should leave `queued`, `processing`, or due `retry` within
15 minutes, measured over a rolling 30-day window. No processing lease may
remain older than `JOB_CLAIM_TTL_SECONDS` for two consecutive one-minute health
samples. A missed target opens an incident and blocks release promotion until
the recovery path is evidenced.

## Release evidence checklist

Run the following against one exact release commit and record UTC timestamps:

1. Confirm GitHub API and web CI jobs passed on the exact head SHA.
2. Confirm `/health` has `ready=true`, every dependency is available, the
   descriptor-derived expected queue list has no missing entry, and beat age is
   below `BEAT_STALE_AFTER_SECONDS`.
3. Submit one metadata-only import with a caller-supplied `X-Request-ID` and
   prove API dispatch, provider worker, and process worker logs share its
   `job_id` without exposing secrets.
4. Create or identify a controlled dead-letter row and show
   `dead_letter_growth` activates without exposing the row or error message in
   public health. Preserve the row afterward.
5. Interrupt Redis without deleting its AOF volume; prove a queued job, a due
   retry, and an expired processing lease recover once after Redis returns.
6. Confirm provider quota and robots-policy failures activate their aggregate
   warning conditions and do not trigger media acquisition.
7. Record the Compose project name, image IDs, deployment commit, health
   summary, test run IDs, and rollback result. Attach only sanitized evidence
   to issues #4 and #6.

## Retention and secret-redaction audit

Before release, review a bounded sample from each backend service and search for
`Bearer `, `postgresql://`, `redis://`, `service_role`, `api_key`, `password`,
and known secret suffixes. Any match containing a real value fails the gate.
The host retains approximately 50 MB per container; configure the external sink
according to the organization retention policy and access controls.

## Rollback

Use the non-destructive procedure in
[`deployment-production.md`](deployment-production.md#rollback). Keep the
PostgreSQL rows and Redis AOF volume. After rollback, verify public health,
descriptor-derived worker queues, beat freshness, one authenticated read, and
one metadata-only import correlation trail. Never use `docker compose down -v`.
